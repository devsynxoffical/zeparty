17. User & Merchant Refund Requests

Reference image — User & Merchant Refund Requests
What this section does
This section is the central refund-request workflow for Users and Merchants. It must allow authorized Admin/Finance staff to review refund requests, verify the original transaction, choose a full or partial refund, apply a custom amount, and safely reverse or correct the related coin/payment records.
Required account types
User Refunds
Coin Seller / Reseller Refunds
Merchant Refunds
Required filters and search
Search by requester name, User ID, Seller ID, Merchant ID or Refund Request ID.
Search by original Transaction ID / Chain ID.
Filter by country.
Filter by account type: User / Coin Seller / Merchant.
Filter by status: Pending Review, Approved, Rejected, Partially Refunded, Fully Refunded, Held and Cancelled.
Filter by date range and refund reason.
Refund review screen
Show requester profile and account type.
Show original transaction details, payment method, amount, coins and timestamp.
Show current balance and affected downstream transfers/gifts where applicable.
Show requested refund amount and maximum refundable amount.
Show refund reason, user notes and uploaded proof/evidence.
Show whether the transaction has already been spent, transferred or settled.
Refund actions
Full Refund — refund the complete eligible amount.
Partial Refund — refund a selected portion only.
Custom Amount — Admin can enter an exact amount such as 45, 100, 200 or any permitted value.
Coin Refund — return/deduct the exact coin amount.
Fiat Refund — record the applicable fiat refund amount where the payment channel supports it.
Approve Refund.
Reject Refund with mandatory reason.
Put on Hold for additional verification.
Cancel an unprocessed request.
Create a manual correction when the original refund request is incorrect.
Automatic refund / correction logic
The system should support configurable automatic rules. For example, if duplicate coin credit, duplicate recharge or a verified over-credit is detected, the system can create a refund/correction request automatically. The Admin must be able to enable/disable these rules and define thresholds.
Automatic duplicate transaction detection.
Automatic excess coin detection.
Automatic calculation of refundable balance.
Automatic creation of a correction/refund request.
Automatic approval only below a configurable low-risk threshold, if enabled.
Mandatory Finance/Super Admin approval above the configured threshold.
Downstream impact protection
If refunded coins have already been gifted, transferred or converted, do not silently remove the balance.
Open a Downstream Review showing all affected accounts and transactions.
Calculate the net amount that can safely be reversed.
Create linked reversal/correction transactions for every affected balance.
Require higher-level approval for high-risk or cross-account corrections.
Security & audit requirements
Every refund must have a unique Refund ID.
Every refund must link to the original Transaction ID and Chain ID.
Record old balance, refund amount and new balance.
Record operator/Admin ID, approval Admin ID and timestamps.
Refund records must not be hard-deleted.
A rejected or cancelled request remains visible in the audit history.
Large refunds and cross-account corrections require configurable multi-step approval.
Developer workflow
Refund Request → Identity & Transaction Verification → Eligibility Check → Downstream Review → Full/Partial/Custom Refund Selection → Approval Rules → Execute Refund/Correction → Update Balances → Write Immutable Ledger Event → Notify relevant account → Close Request.
Recommended UI buttons
Review Request | Full Refund | Partial Refund | Custom Amount | Approve | Reject | Hold | Cancel | Downstream Review | View Original Transaction | View Chain Trace | View Account | View Audit Log

20. Global & Country / Region Asset Control

Reference image — Add New Virtual Asset / Asset Configuration

Reference image — ZeParty Asset Library
Purpose
Expand the Asset Library so the Super Admin can control every virtual asset in the app from one Admin Panel. The same asset can have a Global configuration for the entire platform or a Country/Region-specific configuration that overrides the Global configuration only for selected markets.
Top-Level Scope Selector
Global — applies to the entire app and all countries/regions unless a more specific override exists.
Country — select one country and configure assets specifically for users of that country.
Region — select a defined region/group of countries and configure assets for that region.
Country/Region inheritance must be explicit and visible so Admin knows which configuration is currently active.
Priority rule: Country override > Region override > Global default.
Admin must be able to reset a Country/Region override and fall back to Global.

Role/Level eligibility.
VIP/SVIP eligibility.
Country/Region availability.

Display frequency/cooldown where applicable.
Maximum purchase/use limits where applicable.
Global vs Country/Region Override
When an Admin changes an asset under Global, the change applies platform-wide. When the Admin selects a Country or Region, the Admin can override the Global value only for that scope. The UI must clearly show whether each field is inherited from Global or overridden locally.
Example: Global Gift A = 1,000 coins.
Pakistan override = 800 coins.
UAE override = 1,200 coins.
All other countries continue using the Global 1,000-coin price.
If Pakistan override is removed, Pakistan automatically returns to the Global value.

Safety, Permissions & Audit
Only authorized Admin roles can change global financial values such as gift prices.
High-impact changes can require Finance/Super Admin approval.
Every price/media/availability change must create an audit record.
Audit record must contain Asset ID, scope, country/region, old value, new value, Admin ID and timestamp.
Do not silently overwrite Global settings when editing a Country/Region override.
Show a confirmation summary before publishing high-impact changes.
Support rollback/reset of the latest configuration change where technically safe.
Developer Data Model
Recommended configuration model: Asset Master → Global Configuration → Region Override(s) → Country Override(s). Each override stores only changed fields and inherits all other fields from its parent scope.
Developer Workflow
Open Asset Library → Select Global/Country/Region → Search Asset → Open Asset → Edit configuration → Preview effective configuration → Confirm → Approval if required → Publish → Write Audit Log.
Effective Configuration Preview
Before saving, show the Admin the final values that users in the selected scope will receive. For example: Global Price 1,000 → Region Override 900 → Country Override 800 → Effective Price 800.

34.6 Final Owner-vs-Developer Boundary
OWNER/SUPER ADMIN = business rules, prices, rates, commissions, targets, limits, countries, content, gifts, virtual assets, store items, games, PK/events, rankings, referrals, banners, announcements, room-theme approvals, users, hosts, agencies, sellers, merchants, refunds, withdrawals, moderation, notifications, permissions and operational workflows.
DEVELOPER/TECHNICAL TEAM = source-code changes, new backend capabilities, new integrations, database/infrastructure changes, native mobile changes, security fixes, unsupported media/code support, deployment/build/release work and technical incident recovery.
34.7 Final Acceptance Requirement
The developer must not hard-code any business value that is listed as Admin-configurable. Before final delivery, the developer must demonstrate each configurable control in a staging environment and provide a written checklist confirming that changing the value in Admin Panel changes the live application behavior without code modification or database manual editing.
The developer must also provide an Admin-only emergency control for each high-risk module: payments/recharge, withdrawals, gifts, games, PK/events, rankings, referrals, banners, announcements, room themes and notifications.
